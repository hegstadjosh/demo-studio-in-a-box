# Judging interface stills

Use this file to judge from a still whether a product interface in the film, recorded or designed, reads as a real, well-made product. Part 1 gives the three published references the source production reviewed interfaces with and the judgments it drew from them. Part 2 ranks the interface defects the source production found most often. A still can show a visual defect; it cannot show whether a retry works or how a wait feels, so check behaviour by playing the cut.

## 1. Three references, three kinds of question

Use whichever reference fits the defect. None of them chooses a product's palette, typeface or personality.

**Dieter Rams: is each element worth its place?** Rams's ten principles for good design, paraphrased: innovation should improve use; a product should be useful; its appearance matters to everyday experience; its operation should be understandable; it should show restraint; it should be honest and not imply value it lacks; it should last; its details should be resolved with care; it should spend resources responsibly; and it should keep what matters and remove the rest. For an interface still, ask what the person on screen is trying to do and whether each visible element serves that activity. A score panel that looks attractive but gives no reason for the score fails usefulness however well it animates. From the source production's design reviews: atmosphere, characters and humour can be part of a product's value, so stripping them to make a screen sparse is not restraint; and awkward wrapping or a cramped phone control is a product defect, not a cosmetic one.

**Nielsen's ten usability heuristics: does the interface behave predictably?** Paraphrased, they ask whether the interface shows what is happening promptly; uses the viewer's language and expected order; offers exits and undo; keeps established meanings consistent; prevents avoidable errors; shows choices instead of requiring recall; serves newcomers and experienced users; keeps irrelevant material out of the task; explains errors plainly with a remedy; and gives brief, task-specific help. Nielsen's own emphasis on status distinguishes an action being received from an action succeeding, and warns against inventing a progress figure or a timing promise. From the source production's design reviews: rank findings by how much they hurt, how widely they recur and whether they can be recovered from, rather than ticking the ten heuristics as equal boxes; and prefer removing a needless step to adding a tooltip or confirmation.

**Refactoring UI: is the visual execution sound?** Adam Wathan and Steve Schoger's public guidance, paraphrased: build hierarchy with weight and colour, not only size; tint secondary text to suit a coloured background instead of using a flat grey; give shadows a direction; separate regions with spacing or contrasting surfaces before adding borders; keep icons near the size they were drawn for; use accent colour sparingly; and style actions by priority (strong, quiet, text-like) rather than by whether they are positive or negative. From the source production's design reviews: compare components that do the same job across screens and make any difference deliberate; inspect each component in context as well as cropped; check narrow layouts, long text, focus, loading, empty and error states; treat reduced emphasis as a visual relationship, never as permission to make text unreadable; never signal state by colour alone; and use the product's existing tokens instead of inventing new ones.

**How to report a finding.** State what the still shows, the viewer's likely difficulty, the reference that explains it, and a change you can check by rendering the same state again. Keep three kinds of decision apart: principles (qualities wanted, such as understandable feedback), shared patterns (one reusable solution, such as how a score change is shown) and visual choices (type, spacing, colour). Consistency helps a viewer transfer understanding, but copying an existing flaw does not. Say which claims you checked and which remain hypotheses, and do not present taste or a source author's advice as a decision the product's owner has made.

## 2. Ranked defects

All of this section is from the source production's design reviews. The ranking weighs how much a defect hurts the viewer, how many screens it appears on and how strong the evidence is. The source review's main conclusion was that these defects recur because each screen solves the same job separately, so the fix is one shared component per job, not a patch per screen.

1. **One job, many controls.** The same function (a scoreboard, a rules dialog, a text input, a settings menu, a back button) looks, sizes or is labelled differently from screen to screen. It hurts because the viewer must relearn each screen, and cutting between screens exposes the mismatch. Check: line up stills of every screen in the film and compare each recurring function's shape, size, wording and position.

2. **Scores and results that are wrong, stale or unexplained.** A summary that reverses the point it credits, a result contradicting its own timer, a total changing with no reason shown, two displays of one score disagreeing. It hurts most because a score is the payoff the viewer is following, and an unexplained one cannot be trusted or learned from. Check: read every number in the still, add it up, compare it with the other displays and the narration, and confirm a reason sits beside each change.

3. **Phone layouts that break.** Content wider than the screen, buttons clipped or pushed outside their card, titles truncated, adjacent numbers merging (a 5 to 2 score reading as 52), panels covering the content, menus that close without opening. It hurts because most viewers watch on a phone and take the phone view as the product. Check: inspect the still at the target phone width for clipped edges, ellipses, merged figures and overlapping layers.

4. **Invented, inconsistent or stale wording.** Coined phrases where standard words exist, one thing called by several names, help text describing rules that no longer apply, labels contradicting the product's real state. It hurts because the viewer stops to decode the word instead of following the scene. Check: read every label aloud, ask whether a newcomer would use that word, and confirm one name per thing across the film.

5. **Clutter.** Text floating with no container, setup notes styled like messages, extra panels appearing all at once, too many labelled buttons in a header, stray rules at different heights. It hurts because the viewer cannot find where to look. Check: every piece of text belongs to a visible container, and each moment shows only what that moment needs.

6. **Dead ends.** A result, refusal or failure screen with no next step: a bare error, a raw technical message, a spinner that never resolves, an end screen whose only exit is home. It hurts because the viewer sees the product abandon its user. Check: every terminal state in the still offers a plain explanation and a visible way forward.

7. **Losing the user's place.** After a reload, sign-in or gate, the user lands somewhere else, progress resets or a session restarts. A still rarely shows this; check it in the sequence of shots, and never depict continuity the product lacks.

8. **Waits that look broken.** An action with no visible acknowledgement, a connection screen giving no confidence, feedback that arrives after the user has moved on. It hurts because the viewer reads silence as failure. Check: the frame after each action shows that the action was received.

9. **Controls that do not look or behave like controls.** An action available only through underlined text, menus that vanish on opening, unlabelled progress dots, a button styled after an unrelated product. Check: every interactive element is recognisable as interactive and labelled.

10. **Promises the product does not keep, and failures shown as empty states.** Copy advertising a feature that does not exist or is already free, settings that do nothing, a failed load shown as an empty record. It hurts honesty directly. Check each claim against the truth list, and treat any empty state as a possible hidden failure.

11. **Not everyone can read or use it.** Low-contrast text (dark on near-black), one side's figures harder to read than the other's, missing focus rings, a voice-only mode with no captions. Check: contrast against the actual background, and that no state relies on colour alone.
